# Architecture

```
┌──────────────────────── Renderer (sandboxed, contextIsolation) ───────────────────────┐
│ React UI: sidebar, toolbar, split tree, dialogs, command palette                      │
│ TerminalController per pane: xterm.js instance + session, kept outside React          │
│ No Node.js/Electron access. Talks only to window.appApi                    │
└───────────────▲───────────────────────────────────────────────────────────────────────┘
                │ preload (contextBridge): 16 named methods, no raw ipcRenderer
┌───────────────┴──────────────── Main process ─────────────────────────────────────────┐
│ ipc.ts            sender check (main window + trusted app URL) on every message        │
│ session-broker.ts session IDs, ownership (webContents) + pane, input/size validation   │
│ launch-resolver   workspace → profile → executable → folder → WSL path → launch spec   │
│ shells.ts / wsl.ts  discovery (pwsh, Windows PowerShell, wsl --list), wslpath mapping   │
│ state-store.ts    versioned JSON, atomic + debounced writes, corrupt-file preservation │
│ main.ts           window lifecycle, CSP/navigation/permission policy, quit confirmation │
└───────────────▲───────────────────────────────────────────────────────────────────────┘
                │ utilityProcess MessagePort (spawn/input/resize/ack/kill ⇄ spawned/data/resized/exit)
┌───────────────┴──────────────── PTY host (Electron utility process) ──────────────────┐
│ session-manager.ts  node-pty (system ConPTY), output batching, flow control, cleanup   │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

## Key decisions

- **Electron Forge 7.11 + Vite 5.** Forge 8 requires Node ≥ 22.13; the machine has Node 20.19.5, and installing system software was out of scope. The Forge Vite plugin packages only `.vite/` by default, so `forge.config.ts` adds an explicit `ignore` filter that also keeps node-pty’s runtime files. It unpacks them from the ASAR archive (`asar.unpack: **/node_modules/node-pty/**`) because they include native `.node` files, `conpty.dll`, `OpenConsole.exe`, and a worker script loaded by path.
- **node-pty 1.1.0 in a utility process.** It has N-API prebuilds, so no Electron rebuild is needed. The main process passes the absolute module path (`app.asar.unpacked/...` when packaged) to the utility process, which loads it with `createRequire`.
- **xterm `windowsPty` + `reflowCursorLine`.** With `windowsPty`, xterm adds blank rows when a pane grows (as ConPTY does) instead of pulling scrollback down; `reflowCursorLine` rejoins a wrapped prompt when a pane widens. Remaining gap: when *widening* rejoins wrapped lines, xterm still pulls scrollback into the viewport and ConPTY's repaint overwrites it (TESTING.md).
- **System ConPTY + fork guard.** The bundled conpty.dll never repaints after a resize and relies on the terminal re-wrapping exactly as conhost does; xterm.js does not (measured: 35 of 64 screen checks differed). The system ConPTY repaints, so SplitNest uses it (`useConptyDll: false`; `TW_DIAG_CONPTY=bundled` switches back in development for diagnostics). Its `kill()` in node-pty 1.1.0 forks `conpty_console_list_agent`, which in the packaged app (RunAsNode fuse off) would start a second SplitNest; `src/pty-host/fork-guard.ts`, installed before node-pty loads, answers that request in-process with the shell PID and refuses all other forks. Verified in the packaged app: shells, foreground children and console hosts end, and no second instance starts (`tests/e2e/verify-packaged-close.ps1`).
- **Resize path** (`terminal-controller.ts`). A ResizeObserver schedules a fit on a timer task (never in requestAnimationFrame: the WebGL canvas would be cleared one frame before it is redrawn, a visible flash), at most every 50 ms. The proposed size goes to the PTY host first; it applies it and answers `resized`. Only then, after the output received before that answer has been parsed (`term.write("", cb)`), does xterm resize. One request is in flight at a time; the newest size is sent after each answer, so the final size always lands, and a 1 s timeout covers a lost answer. The host applies a resize only once the console's redraw for the previous one has arrived and gone quiet (30 ms, at most 250 ms), so a redraw is never laid out at the wrong width. Tabs without a running session resize xterm only.
- **Scrollback boundary** (system ConPTY). The console has no scrollback and redraws its whole screen after a resize, keeping the text of its top row at the top; xterm re-wraps everything and keeps the cursor's row in place instead, which moves the boundary between scrollback and screen (widening pulled scrollback rows onto the screen, which the redraw then overwrote; narrowing pushed screen rows into scrollback, which the redraw drew again). After a confirmed resize the controller holds the session's output, re-wraps, finds the console's top row, makes that row the top of xterm's screen with resizes that keep the screen filled (`windowsPty` is unset for one resize to take rows back from scrollback), and then writes the held redraw. The top row is found from the first rows of the console's redraw, located in xterm's buffer near an estimate from markers (the estimate alone when they cannot be matched). Those rows are laid out by a second xterm that is never shown, with the same size and Unicode version (`redraw-reader.ts`): SplitNest interprets no escape sequence of the output itself, and the rows are by construction the ones the terminal will have (combining marks, double-width characters, cursor moves). Output is never held longer than 1 s, and any error falls back to a plain resize.
- **Cut lines** (`cut-line.ts`). If the console's top row was the second or later row of a wrapped line and the new width splits that line elsewhere, the console only has the rest of the line and redraws it as a line of its own; xterm keeps the complete line in scrollback and shows the console's part on the top row, as the console does. The controller puts a marker on that row. Once output has scrolled it off the screen the rows are deleted from scrollback with public xterm operations only: grow the terminal by the distance (rows return from scrollback), delete the lines at the top (DL), shrink back. The rows are identified by the marker (where they came from), never by their text; the text is checked in addition. It is only done with the cursor on the last row, the view at the bottom, no selection, and at most one screen height above the screen; otherwise the part stays.
- **One output path** (`TerminalController.out`). Everything written to xterm goes through one ordered queue: it waits while a resize is being applied or a cut line's part is being removed (no fit starts then either), and it is given to xterm line by line while such a part is still on the screen, so the removal happens right when the part has left it.
- **Own split tree instead of a panel library.** The persisted model is an n-ary tree (`pane` leaves; `split` nodes with direction, children and normalized sizes). Splitting in the parent’s direction adds a sibling instead of nesting. Closing redistributes space and collapses single-child splits, and depth is capped at 8. Rendering is a ~150-line recursive component with pointer and keyboard dividers. This avoided an API-churning dependency (react-resizable-panels v4).
- **Terminals outside React.** A `TerminalController` owns each xterm instance and its persistent DOM element. React panes only attach and detach that element, so splitting (which re-parents panes), switching workspaces (hidden with `display:none`) and StrictMode double effects never recreate a terminal or a process. Output is written straight to xterm and never goes through React state.
- **React state** via `useReducer` (pure reducer in `workspace-state.ts`) plus `useSyncExternalStore` for per-pane session status. No external store.

## Git status

- `GitStatusService` (main) keeps the last state per workspace and pushes changes to the page (`tw:git:status`); the page asks with
  `tw:git:refresh` when the user selects a workspace or the window gets focus, and reads everything once at start (`tw:git:statuses`).
- One check = `git status --porcelain=v2 --branch --untracked-files=normal -z`, then, only when tracked files changed,
  one `git diff --shortstat HEAD`: the working copy of tracked files against the last commit, staged and unstaged together (English
  output via `LC_ALL=C`). Before the first commit the same single diff runs against the empty tree, whose id Git computes for the
  repository's object format (`git hash-object -t tree --stdin` with empty input: SHA-1 or SHA-256; nothing is written). One check runs at a
  time for all workspaces; results are published only when they differ.
- Terminal output reaches it from the session broker (`onOutput(workspaceId)`, no extra IPC): a check follows 0.8 s after output stops,
  at least 3 s after the previous one; continuous output causes one at most every 30 s. Requests (select, focus, file save) run at once; within a
  second of the last check, one check is scheduled for the moment that second ends (further requests join it; turning the setting
  off or removing the workspace cancels it). A request while a check runs goes the same way when that check ends, so the second
  counts from the start of that check and checks never overlap.
- Untracked entries from `--untracked-files=normal` are not a number of files (a new folder is one entry), so the page only says
  "Untracked files present" (tooltip and accessible description).
- Workspaces inside WSL (`\\wsl$\…`, `\\wsl.localhost\…`) are skipped: Windows Git over that share is slow and refuses those
  repositories as owned by another user. The terminal's shell does not matter.

## Agent inbox

- **State.** `AgentNotifier` keeps one inbox item per tab next to its notices (`TabState.pending`), from the same events: a "needs you" item lasts while the agent is blocked (seeing the tab doesn't clear it); a finished turn or an error lasts until `reviewSeen()` finds the user looking at the tab, or the agent works again. `inbox()` returns them sorted by `sortInbox` (needs you, errors, finished; oldest first). Nothing is persisted.
- **UI.** `useAgentNotifications` exposes the list; `App` turns items into rows with the notices' own wording (`noticeTitle` / `noticeBody`, so the details setting applies) and renders `AgentInbox` in the title bar. `nextInboxItem` picks the target of the "next agent" shortcut relative to the tab in front.

## Agent session resume

- **Capture (main).** `agent-sessions.ts` (`AgentSessionTracker`), fed by `AgentMonitor` on every process scan with the agent process `findAgent` matched under the tab's shell.
  - **Claude Code:** `~/.claude/sessions/<pid>.json` of that process (exact; re-read each scan because `/clear` changes the id).
  - **Codex:** the id in `codex resume <id>`, else the single rollout (`~/.codex/sessions/…`, first line only) started in the tab's folder after the agent was first seen and not claimed by another tab, else none (the agent's picker).
  - Only metadata is read. Ids must be UUIDs and folders absolute (`shared/agent-resume.ts`).
- **Saved (renderer).** `IPC.sessionResume` → `TerminalTab.resume` via `setTabResume`; validated on load (a bad record drops only Resume). Main stops the monitor before ending shells at quit, so quitting doesn't clear it.
- **Resume.** `TerminalController.resume()` starts PowerShell with `startPath` (main checks: inside the workspace folder, exists, not WSL), waits for the prompt (output, then 600 ms quiet), and writes `resumeCommand()` (built from the agent id and a validated UUID only). If process detection doesn't find that agent within 25 s, the pane says so.

## Agent notifications

- **Detection (renderer).** `features/notifications/agent-notifier.ts` turns each terminal's agent view into events: needs you, finished, error. The views come from `deriveAgentView`, which reads the agent's OSC 7501 reports.
  - **Pure logic:** timers and the window/tab situation are injected, and the tests replay recorded Claude Code and Codex runs (`tests/fixtures/agent-status-recordings.json`).
  - **Finished:** only a reported `done`. It is latched when it arrives (Codex replaces it with `idle` within a second) and held for 1.5 s in case the agent works again. It survives the agent's exit.
- **Where it goes.** `useAgentNotifications.ts` decides:
  - nothing for the tab on screen;
  - an in-app notice when the window is focused;
  - otherwise a request to main.
- **Focus comes from main.** The page's own `document.hasFocus()` and `visibilityState` stay true/visible while the window is minimized or behind another program (measured with Electron 45), so main sends the real state over `IPC.windowFocus`.
- **Text (main).** `src/main/notifications.ts` writes all Windows notification text from the event kind, the agent id, and the workspace and tab names in main's saved state (`shared/notifications.ts`, shared with the in-app notice).
  - **Agent's own text:** session title and message are used only with *Include what the agent wrote*.
  - **Validation:** the page's request is checked whole (ids, kind, agent id, app name, lengths).
- **Identity.** A Windows notification needs `AgentView.confirmed`: process detection found the agent the reports name, or detection isn't available (WSL). An unconfirmed "needs you" waits for confirmation; other unconfirmed events stay in-app.
- **Clicks.**
  - **Routing:** each notification's `click` event, through main's notification → tab map. Windows' activation arguments are empty for Electron notifications (measured).
  - **Effect:** main restores and focuses the window and sends `IPC.notifyActivate`; the page checks the tab still exists and shows it.
  - **Fallback:** `Notification.handleActivation` only brings the window up, for clicks without a live object.
- **Lifetime.** One notification per tab, replaced by newer ones; more than 3 within 10 s become a summary.
  - **Withdrawn when:** the agent moves on or the user sees the tab, through `Notification.close()`, which also removes it from Notification Center.
  - **On quit:** all are closed, because a leftover entry would start the build that last notified, without its profile argument.
- **Windows registration (Electron 45, measured).** The first notification creates a Start menu shortcut (`SplitNest.lnk`, AUMID `electron.app.SplitNest`) and a per-user COM activator. Both are re-pointed at the exe of each build that notifies. SplitNest doesn't set its own AUMID or activator CLSID. Windows accepts the notification that causes this registration but doesn't display it, so `showAgainOnceRegistered` (main) shows a notification again after 3 s when the shortcut didn't exist before it (and any other shown inside those 3 s); same id, so it replaces the invisible one.
- **Tests.** E2E builds record notifications in `globalThis.__twNotices` instead of showing them (unpackaged, `TW_E2E=1` only), so tests never touch Notification Center or the Start menu.
- **Packaged checks.** `--tw-notify-id=<token>` prefixes notification ids (toast tags) with a run token. `tests/windows/notifications.ps1` reads Windows' notification history only for SplitNest's app id and that token, before any text, and prints ids and pass/fail only.

## Session lifecycle

1. The renderer flushes pending state, then calls `createSession({workspaceId, paneId, profileId, startIn, cols, rows})` (`paneId` is the terminal tab's id). Each `TerminalController` routes every start through a `StartGate` (`bulk-start.ts`): while one start is in flight, a second click, **Start all shells** or Ctrl+Shift+R joins it instead of starting another session. Restoring a layout never calls `createSession`; only an explicit Start (or the opt-in "start fresh shells" setting) does.
2. Main validates the request and rejects a second concurrent session for the same pane. It looks up the workspace in **its own** validated state, checks the profile against discovery, re-checks the executable and folder, and (for WSL) maps the folder with `wslpath` and `test -d`. It then sends a spawn spec with **structured arguments** (`-NoLogo`, or `--distribution <name> --cd <linux path>`). Folder and distribution names are never concatenated into a command string.
3. The PTY host spawns and batches output (4 ms or 64 K characters). Main forwards the output only to the owning webContents.
4. **Flow control:** the renderer acknowledges characters after xterm has parsed them. Above 512 K unacknowledged characters the PTY host pauses the PTY, and resumes below 128 K. Nothing is discarded; the program writing output is simply back-pressured.
5. Exit: output arriving up to 60 ms after the exit notification is still delivered, then the exit code is reported, the session is removed and listeners are disposed.
6. Close/kill: output stops being delivered, the PTY is resumed (so ConPTY can drain) and killed. If no exit is reported within 4 s, the session is reported as ended anyway.
7. If the PTY host crashes, every session is reported as ended and the host restarts on the next spawn. A renderer reload or crash ends that renderer’s sessions.

## Security boundaries

- `contextIsolation`, `sandbox`, no `nodeIntegration`, no `webviewTag`, and DevTools only in unpacked builds. The application menu is removed, so its accelerators can’t steal terminal keys.
- Production CSP: `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; …`. Inline styles are needed by xterm. The dev server gets a relaxed policy only while serving.
- Navigation, redirects, new windows and webviews are blocked. All permission requests and checks are denied.
- Every IPC message must come from the main window’s **top frame** at the trusted app URL. Inputs are type-, size- and range-checked. Session IDs must belong to the calling webContents, and stale or unknown IDs are rejected.
- `saveState` accepts only workspace folders that came from disk or from the native folder picker, so a compromised page can’t invent a launch directory.
- Terminal output is untrusted. It is rendered only by xterm (never as HTML) and cannot write the clipboard (no OSC 52 handler). Links open only on Ctrl+click, and main allows `http`/`https` only.
- **File editor access** (`src/main/file-editor.ts`): `readFile`, `statFile` and `writeFile` take a workspace id plus a relative path. Main resolves the path against **its own** copy of the workspace root and rejects `..`, absolute, UNC, drive, stream and wildcard paths.
  - Only existing regular files up to 5 MB are read or written; nothing is ever created, renamed or deleted.
  - Writes are refused when the real path (after links and junctions) leaves the workspace folder, and when the file's mtime differs from the version the editor read (`CONFLICT`), unless the user explicitly chose *Overwrite*.
  - Files are written in place, so permissions, hard links and identity are kept. Contents are never logged; failures log only an error code.
  - **Versions are content hashes.** `readFile`/`statFile`/`writeFile` report a SHA-256 of the file's bytes. A save sends the hash it is based on; main re-reads and re-hashes the file right before writing and refuses with `CONFLICT` on any difference. Timestamps are only informational.
    - Remaining race: a write by another program between that check and SplitNest's write is not detected. Windows has no portable compare-and-swap for in-place writes.
  - **Watching** (`src/main/file-watch.ts`): each open file's parent folder is watched with `fs.watch`, so atomic replacement (rename over) and delete/re-create keep being seen.
    - Events are matched by file name and debounced (150 ms), and the number of watched files is capped (256). Watches are ref-counted per renderer and released when a tab closes or the page reloads.
    - Events are only hints: the renderer re-hashes the file, which filters out SplitNest's own saves and no-op touches.
    - If the watched folder itself disappears, every file in it is reported once and that watch ends; the focus check remains as a fallback.
  - **Quit flow** (`src/main/quit-flow.ts`): window close and app quit both pass through one coordinator. It asks once (repeated requests are absorbed while a dialog or save is pending). *Save all* sends `save-all-request` to the page, waits for the result (120 s timeout = failure), and quits only if every dirty editor was written and none are left dirty.
- Shells run with the user’s normal privileges. Electron-internal variables (`ELECTRON_*`, `VITE_*`, `NODE_ENV`) are removed from their environment.
- Fuses: `RunAsNode`, `NODE_OPTIONS` and `--inspect` are disabled; ASAR integrity validation and only-load-from-ASAR are enabled.
- Development-only hooks (`TW_E2E=1`, `TW_E2E_PICK_FOLDER`) are honoured only when `app.isPackaged` is false.
- Git status (`src/main/git-status.ts`) runs `git.exe` (found on PATH once) only in main, with structured arguments, a timeout and an output cap, against main's own copy of each workspace root; the page sends workspace ids only. Checks are read-only (`--no-optional-locks`, `GIT_OPTIONAL_LOCKS=0`) and switch off settings with which a repository could make Git start a program during `status` or `diff` (`core.fsmonitor=false`, `--no-ext-diff`, `--no-textconv`); variables that would point Git elsewhere (`GIT_DIR`, `GIT_WORK_TREE`, …) are removed, and `GIT_CEILING_DIRECTORIES` adds the user's home folder and the drive root. Git's own `safe.directory` check is not overridden. Clean filters (`filter.<name>.clean`/`.process`), which `git diff` starts to compare working-tree files, are checked first: if the repository's own configuration (local or worktree scope, includes followed) sets one, only the branch is read (`symbolic-ref`, `rev-parse`, which look at no file) and the page says changes were not checked. Filters from the user's global or system configuration (e.g. Git LFS) apply as in any Git tool. `status` and `diff` run with `--ignore-submodules=all`: Git would otherwise check each submodule with that submodule's own configuration, filters included, which the check above does not read; changes inside submodules are not counted. Nothing about repositories is logged.

## Extending later

- New platforms: shell discovery (`shells.ts`), launch construction (`buildLaunch`), the ConPTY choice and the fork guard are the Windows-specific seams.
- New shell kinds: add a `ShellKind`, discover it in `discoverShells`, and build its arguments in `buildLaunch`.
- Shell integration (cwd tracking, command status) would attach to `TerminalController` and must not change what the pane header claims until it exists.
